# Review of the Minigraph-Cactus draft plan

Reviewed `MINIGRAPH_CACTUS_PLAN_DRAFT.md` against this repository, the mounted QC list and reference indexes, and the [official Cactus pangenome documentation](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md). This is a design review only; no workflow or FASTA scan was run locally.

## Required before implementation (P0)

1. **Make every seqfile FASTA path valid on the server.** The 196 QC-list entries are already absolute `/gpfs/...` paths, but `pangenome.references.CHM13` and `.hg38` are `../refs/...`. If those strings are copied into a seqfile under a results `metadata/` directory, their meaning is ambiguous and they may point at the wrong directory. Use the top-level `references` values, which already contain server-absolute paths, or explicitly construct server-absolute paths from `workflow_root` without `realpath`. State the launch working directory and validate that every emitted path is absolute and readable *on the server*. Keep the input list itself as a tracked Snakemake input. [Cactus seqfile format](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#interface).

2. **Specify a safe Toil/Snakemake restart state machine.** `--restart` applies only to an existing unfinished Toil workflow in its job store. Toil's default is `--clean=onSuccess`: a Cactus success can remove the job store before the Snakemake marker is written, and an incomplete marker can also mean a failed output check rather than an interrupted Cactus run. Do not infer restart merely from the existence of the store or from `--rerun-incomplete`. On a fresh run require a new/empty store and output directory; on failure retain the store and partial outputs; on restart require the same immutable input/config fingerprint and an unfinished store; on a completed Cactus run with a missing marker, verify the output files and publish the marker without relaunching. Make Cactus's `--clean` policy explicit. Reject an occupied store belonging to a different build and prevent concurrent launch against one store. [Toil job-store, cleanup and restart options](https://toil.readthedocs.io/en/releases-9.0.0/running/cliOptions.html#commandline-options).

3. **Tie a build to its exact settings and inputs.** A seqfile hash alone misses changes to Cactus version, reference FASTAs, clipping/filtering and resource/runtime options. Put a stable build ID or full settings fingerprint in the metadata and isolate its `jobStore` and `outDir`. Have the Snakemake rule track the two reference FASTAs and the inclusion list as inputs, and put all output-affecting options in `params` or a tracked config snapshot. On a changed build, fail clearly or use fresh output/store paths; never restart stale state. A marker-only output avoids Snakemake deleting a partial Cactus tree, but a surviving marker also lets Snakemake overlook subsequently deleted graph files. Provide an explicit server-side output verification command/target (or a checked output manifest) that tests the files listed below, even after a prior successful run.

4. **Resolve resource accounting by Toil batch mode.** `--batchSystem` defaults to `single_machine`. In that mode the Snakemake job must have CPU, memory and disk for *all* concurrent Toil work, and Toil's `--maxCores`/`--maxMemory` must fit the allocation. With a scheduler-backed Toil batch system, Snakemake's resource request mainly covers the Toil leader/driver while Toil separately submits workers; the leader must run where it can submit jobs, access the shared store, and stay alive for the whole build. Make the two modes explicit rather than giving one `threads`/`mem_mb` setting both meanings. The `--workDir` value must be an absolute path available on each worker (and shared if worker logs/cache need sharing). Keep its capacity and Toil `--maxDisk` distinct from the job store and final output. [Toil batch-system and workDir options](https://toil.readthedocs.io/en/releases-9.0.0/running/cliOptions.html#commandline-options), [Cactus resource guidance](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#pipeline).

## Required corrections and design details (P1)

5. **Use the observed reference contig sets.** Mounted `.fai` files show CHM13 has `chr1`–`chr22`, `chrX`, `chrY`, **`chrM`** (25 contigs), while `GRCh38_primary_chr1-22_XY.fa` has only the 24 nuclear contigs. Thus there is no GRCh38 mitochondrial path from the current input. This is not necessarily a blocker for a CHM13-backed graph; document it as an intentional asymmetry and report it in preflight. Do not claim matching contig sets or invent an hg38 chrM without a chosen source/build. Confirm the CHM13 version and exact GRCh38 source on the server. Both references have chromosome-scale nuclear contigs and the GRCh38 file has no ALT loci, which is appropriate for Cactus. [Cactus reference and ALT-locus guidance](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#reference-sample).

6. **Validate contig IDs after Cactus's normalization rules, not just raw FASTA IDs.** Cactus strips text through the last `#`, truncates at the first space and replaces non-subrange colons. Two distinct original headers within a FASTA can therefore collapse to one effective ID. Reject collisions and empty IDs after these transformations, and preserve a diagnostic mapping in the manifest. The cleaned FASTAs prefix original IDs, but that does not prove all normalized IDs are safe. Stream this preflight on the execution server; a full pass through 198 human FASTAs will consume time and filesystem bandwidth, so make it a distinct cached/preflight stage rather than repeating it on every restart. [Cactus sample and contig naming rules](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#sample-names).

7. **Correct the output and storage description.** For the proposed switches, expect the clipped `<outName>.gfa.gz`, `<outName>.gbz`, CHM13 `<outName>.vcf.gz` **and its `.tbi`**, `<outName>.raw.vcf.gz` **and its `.tbi`**, filtered `<outName>.d2.gbz/.dist/.min`, `<outName>.sv.gfa.gz`, `<outName>.full.hal`, `<outName>.input-contig-sizes.tsv.gz` and selected `<outName>.stats/` tables. The plan says HAL can be added later, but Cactus's pipeline produces a merged `.full.hal` as part of its output; account for its storage now. `--vcfReference CHM13` does not create a second VCF. The default `.d2` Giraffe files are frequency-filtered, while the plain GFA and GBZ are clipped. `--validate` checks chromosome alignments, and the absence of `.WARNING` is not a substitute for reviewing clipping/accounting reports. [Cactus output and VCF naming](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#output), [statistics reports](https://github.com/ComparativeGenomicsToolkit/cactus/blob/master/doc/pangenome.md#statistics-and-clipping-reports).

8. **Make the standalone entry point concrete.** The root `Snakefile` includes `workflow/rules/pangenome.smk` and others; those files define `configfile` and `workdir`, and `pangenome.smk` itself is a standalone entry point. The new rule file can follow that pattern with one set of rule definitions, `configfile: workflow.source_path("../../config/config.yaml")`, and a workdir based on `workflow.current_basedir` as needed. Do not create a second copy of the build rules or add this expensive target to `rule all`. Use distinct rule names and distinct `minigraph_cactus` config keys so the existing SV-only graph remains independent.

## Good choices to retain (P2)

- The post-decontamination `graph_included_assemblies.txt` is the correct authoritative list. It has 196 paths in the mounted snapshot; the older ordered TSV has 196 assembly rows plus CHM13/hg38 and should only be used to audit, not to impose Mash order. The QC code allows one passing haplotype from a `PARTIAL` sample, so `.1`/`.2` must follow the filename rather than row pairing.
- A single `cactus-pangenome` invocation under one Snakemake rule is sensible: Toil manages chromosome jobs and restart state. Do not feed the existing hand-built `sv_pangenome.minigraph.gfa` to `--inGFA` without a proven matching Cactus construction and seqfile naming policy.
- Cactus 3.3.0 is a current explicit pin, but deployment must be confirmed on the server. Expose the executable/container choice without baking scheduler directives into the rule.
- CHM13 first with GRCh38 as a second `--reference` is supported; only the first is guaranteed un-clipped and acyclic. A CHM13 VCF first is a safe initial choice. The proposed `--gfa --gbz --vcf --giraffe --validate` flags and default `.d2` index names match the official docs. The `--haplo` alternative should remain a separate later mapping profile, since it requires a different read-mapping setup and should not be combined with `--giraffe`.

## Server-only checks before a full launch

Inspect the generated 198-row seqfile and manifest, check the 25/24 reference contig asymmetry, inspect any normalized contig-ID collisions, and confirm every input path and runtime binary from the server. Use a small, isolated pilot with both references and a few accepted haplotypes. Then run `snakemake -n` for the explicit target with the server installation and profile. After the pilot, verify the exact output filenames, nonempty indexes/VCF index, GFA reference walks, clipping/accounting tables, and any `.WARNING` before committing to the 196-haplotype build. No local validation is implied by this review.
