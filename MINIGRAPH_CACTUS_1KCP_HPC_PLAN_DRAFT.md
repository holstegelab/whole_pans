# Draft: scale the local Minigraph-Cactus build on Snellius

This is a design for review, not an executed workflow. `whole_pans/AGENTS.md` prohibits local Snakemake, tests, dry runs, and validation. Server paths below are taken from `config/config.yaml`; this mount cannot establish their runtime identity. Preserve the existing SV-only graph and its rules.

## What the 1KCP example does and does not show

The [1KCP paper's Methods](https://www.nature.com/articles/s41586-026-10315-y) describe a **custom final graph pipeline** for 2,232 haploid assemblies: Minigraph with Mash-based assembly order; assembly-to-graph alignment with filtering; ODGI partitioning into approximately 20 Mb subgraphs; seqwish, three smoothxg rounds, GFAffix, clipping, and k-mer-supported node/edge filtering. The checked-in `1KCP-analysis/02_Pangenome/rules/graph_construction.smk` implements that route, including CHM13 then GRCh38 and increasing Mash distance in its direct `minigraph` command. This final 1KCP graph was **not** made by one `cactus-pangenome` call. The [1KCP supplement](https://static-content.springer.com/esm/art%3A10.1038%2Fs41586-026-10315-y/MediaObjects/41586_2026_10315_MOESM1_ESM.pdf) describes an earlier Minigraph-Cactus graph from CHM13, GRCh38, and 45 1KCP diploid assemblies, used to make personalized references in PIGA. These are distinct graph builds and roles.

The requested deliverable here remains a genuine **Minigraph-Cactus** graph for the 196 cleaned, post-decontamination haplotype FASTAs currently named in `graph_included_assemblies.txt`, plus CHM13 and GRCh38. The count must be derived at execution. Use 1KCP's scale lessons (input QC, explicit graph stages, chromosome-level parallel work, detailed graph QC), but do not copy its ODGI/seqwish model or claim scientific identity with its final 2,232-haplotype resource. A 20 Mb ODGI subgraph workflow would be a later, separately named experiment if conventional Cactus chromosome work proves limiting.

## Recommended build topology

Use the [Cactus v3.3.0 documented five-stage interface](https://github.com/ComparativeGenomicsToolkit/cactus/blob/v3.3.0/doc/pangenome.md#pipeline) under one explicit `minigraph_cactus` target, excluded from `rule all`:

| Snakemake stage | Cactus stage and retained boundary | Why it matters at this size |
| --- | --- | --- |
| `prepare_minigraph_cactus` | Existing seqfile, manifest, contig map, hashes | Freeze selected cleaned inputs once; report 196 as observed, not assumed. |
| `mc_minigraph` | `cactus-minigraph` → cohort SV GFA | The expensive serial graph foundation survives failures in later stages. |
| `mc_graphmap` | `cactus-graphmap` → PAF and graph node FASTA; retain matching GAF if requested | Mapping hundreds of haplotypes is expensive and can be inspected before chromosome assignment. |
| `mc_split` | `cactus-graphmap-split` → `chromfile.txt` and chromosome data | Cactus assigns contigs to reference chromosomes; retain its report of unassigned/filtered contigs. |
| `mc_align` | `cactus-align --batch --pangenome --outVG` → per-chromosome HAL/VG | The batch interface delegates chromosome jobs to Toil; do not invent one Snakemake job per chromosome without proving its input interface. |
| `mc_join` | `cactus-graphmap-join` → final clipped GFA/GBZ, CHM13 VCF, full HAL, optional Giraffe indexes | Isolate the large whole-genome merge and `vg` indexing on a fat node. |
| `minigraph_cactus` | Existing no-output verifier plus deeper QC report | Recheck build identity and output presence on every request. |

Each Cactus command gets a **distinct** shared Toil job store under `<jobstore_root>/<build_id>/<stage>`, a stage log, state, and completion marker. One job store must never be reused by a different stage. Snakemake declares the small marker for a stage, while the stage wrapper checks its nonempty deliverables before atomically publishing the marker; this avoids Snakemake deleting a huge incomplete output directory. Retain stage products after success because they support recovery and audit. `--clean=onSuccess` may remove a successful stage's Toil store, while a failed stage's store remains restartable. A stage can adopt a completed Cactus command only if an exact input/settings fingerprint and recorded exit-zero state exist. Do not infer completion from files alone. Do not auto-delete a store, partial output, or prior build.

The Cactus stage interface should pass `--reference CHM13 GRCh38` consistently and `--vcfReference CHM13` at join. CHM13 remains the chromosome-scale backbone. Keep GRCh38's existing 24 nuclear contigs as a second reference-sense genome; its missing chrM must be reported rather than fabricated. Consider explicit `--refContigs chr1 ... chr22 chrX chrY chrM` after inspecting the CHM13 preflight list on the server; do not use `--noSplit`. Keep default clipping and require the raw/full provenance products. Keep `--gfa --gbz --vcf --giraffe --validate` initially so the output contract and existing guide remain useful. The default `.d2` Giraffe graph excludes singleton nodes; do not treat it as the full graph. If read mapping is a primary next step, compare a separate `--haplo` build/index profile later; Cactus documents that `--haplo` and `--giraffe` must not be combined. See [Cactus's output and indexing documentation](https://github.com/ComparativeGenomicsToolkit/cactus/blob/v3.3.0/doc/pangenome.md#clipping-filtering-and-indexing).

Do not pass the existing independent SV-only GFA as `--inGFA`. That GFA was made with different ordering and tool settings; using it would silently change what this Minigraph-Cactus build means. Cactus v3.3.0 says its own Minigraph stage sorts non-reference genomes by Mash distance internally, so reordering seqfile rows to mirror 1KCP does **not** reproduce 1KCP insertion order. It exposes `minigraphSortInput` in its XML configuration, but there is no evidence that changing this improves the user's Cactus graph. Record Cactus's selected order and version, retain default ordering for the first production build, and make any later order experiment a new build ID.

## Resource and scheduler design for these nodes

Available nodes: 192 cores / 336 GB (small) and 192 cores / 1,440 GB (fat). The earlier local SV Minigraph job reportedly peaked near 83.5 GiB; that is evidence only for **that** command, not a Cactus peak. The Cactus [HPRC example](https://github.com/ComparativeGenomicsToolkit/cactus/blob/v3.3.0/doc/pangenome.md#hprc-graph-running-all-at-once) quotes 64 cores, 512 GB and 3 TB local disk for a smaller human graph. Treat every number below as an allocation to calibrate from the server pilot and stage benchmarks, not a promise that 196 haplotypes fit.

| Stage | First single-machine allocation | Toil controls to start with | Node |
| --- | --- | --- | --- |
| Preflight | 1 core / 8 GB; streaming I/O | None | small |
| Minigraph | 64 cores / 288 GB | `--maxCores 64 --maxMemory 224GiB --mgCores 48 --mgMemory 192GiB` | small |
| Graphmap | 96 cores / 288 GB | `--maxCores 96 --maxMemory 224GiB --mapCores 6` | small, if pilot fits |
| Split | 32 cores / 192 GB | `--maxCores 32 --maxMemory 160GiB` | small |
| Batch align | 96 cores / 1,300 GB | `--maxCores 96 --maxMemory 1TiB --alignCores 16 --consCores 32 --consMemory 256GiB` | fat |
| Join/index | 96 cores / 1,300 GB | `--maxCores 96 --maxMemory 1TiB --indexCores 63 --indexMemory 896GiB` | fat |

Leave about 10–20% memory outside Toil's `--maxMemory` for the leader, filesystem cache, and unmodelled overhead. Each stage's Snakemake `threads`, `mem_mb`, `disk_mb`, `runtime_min`, log, and benchmark must represent its **single-machine aggregate** reservation. The same stage can instead use scheduler-backed Toil after site verification: then Snakemake reserves a modest long-lived leader and Toil requests workers independently. Do not reserve an entire fat node for the leader *and* make it submit another fat worker unintentionally. Keep scheduler options in config/profile, not hardcoded shell directives in the Snakefile. Cactus's [cluster guide](https://github.com/ComparativeGenomicsToolkit/cactus/blob/v3.3.0/doc/progressive.md#running-on-a-cluster) requires a shared job store/output and, if Toil submits SLURM jobs, a worker `--slurmTime`; it recommends batch logs and `--doubleMem true` for OOM retries. Site partitions, walltime limits, max concurrent jobs, and fat-node worker availability need server confirmation before activating that mode.

The current `work_dir: /gpfs/.../toil_work` is suboptimal for heavy temporary I/O. Make `work_dir` optional. On a one-node allocation, prefer the server's node-local `$TMPDIR` (or a documented local scratch path) after checking its **free capacity**; when omitted, Toil uses TMPDIR. For scheduler-backed Toil, each worker needs its own local scratch with the same environment/path semantics; never pass the leader's private scratch directory to workers. Keep stage job stores, immutable inputs, logs, and final results on GPFS. Confirm scratch and GPFS quotas/inodes against the cohort's total compressed FASTA size plus intermediate graph copies; `--maxDisk` is a Toil scheduling ceiling, not a filesystem reservation. Use an isolated shared batch-log directory if scheduler-backed. Because partition and scratch names are site facts absent from this mount, encode them in the server profile/config only after checking them there.

Use two pilot scales: a 2–3 haplotype smoke pilot to check command compatibility and output names, then a representative 12–20 haplotype scaling pilot spanning assembly size, contiguity, sex chromosomes and population diversity. The small pilot will not expose full-cohort join memory. Capture Toil job memory/CPU, Snakemake benchmarks, walltime, output sizes, GPFS and scratch high-water marks. Adjust fat-stage `consMemory`, `indexMemory`, core count and concurrency from those measurements. If a small-node stage exceeds ~288 GB, move **that** stage to fat rather than raising its request past 336 GB. A scheduler-backed mode may reduce elapsed time for independent mapping/chromosome tasks if node quotas permit; retain one-node staged execution as the predictable baseline.

## Inputs, graph identity, and QC

- Continue selecting haplotypes solely from the post-decontamination inclusion list. Preserve a surviving `PARTIAL` sample's actual `.1`/`.2` haplotype. Keep CHM13 first and GRCh38 second in seqfile, then deterministic accepted haplotypes; Cactus's internal insertion order is separate. Freeze each FASTA's decoded-content SHA-256, byte size, mtime, source path, contig headers/effective names, inclusion-list hash, Cactus version, stage options, and reference FASTA provenance under `<results_root>/<build_id>/metadata`. Reusing a build ID with changed content or settings must fail before any expensive stage.
- The current preflight scans every FASTA once; keep it streaming. It must report duplicate Cactus-effective contig IDs, empty sequences, broken gzip/FASTA, header normalization, CHM13/GRCh38 contig sets, assembly count and total bases. Do not rewrite source FASTAs. Compare reference build/version to intended CHM13/GRCh38 coordinate systems on the server.
- At the graphmap/split boundary, inspect the Cactus split log and input-contig accounting. Report per-assembly fraction of bases assigned to chromosomes, filtered/unassigned contigs, large losses, and sex-chromosome behavior. Cactus [documents that stringent small-contig thresholds can drop input](https://github.com/ComparativeGenomicsToolkit/cactus/blob/v3.3.0/doc/pangenome.md#pipeline); use `--permissiveContigFilter` only as a measured, separate build if this happens, since it changes graph content. Chromosome splitting filters interchromosomal events by design; document this interpretation limit.
- At join, check nonempty SV GFA, clipped GFA/GBZ, CHM13 VCF plus tabix index, raw VCF, full HAL, requested `.d2` indexes and Cactus stats; update the exact list against **v3.3.0 pilot output**. Check Cactus `.WARNING`, reference W-walks in GFA, expected sample/haplotype representation, `bcftools view -h`/`tabix -l` readability, reported clipping and graph statistics, and a handful of known regions. Treat file existence as build integrity; biological acceptability requires the QC review. Do not apply 1KCP's k-mer MLP filter without that paper's raw read/k-mer evidence and training model.
